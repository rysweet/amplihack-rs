<system-reminder source="auto-intent-router">
Classify the requested action and its destination before responding.

1. Respect explicit instructions to bypass a workflow.
2. Actual changes to tracked repository files, including documentation wording,
   are Development. Route their implementation through dev-orchestrator.
3. Operations is the canonical class for operations and project management.
   Accept Ops, PM, project management and project-management as equivalent labels.
   Triage, issue creation and assignment, research answers in chat or issues,
   status reporting and coordination use direct execution or one agent with a
   checklist. They do not start default-workflow, create a worktree or create an
   implementation PR. Complexity and requirement counts do not change this rule.
4. Mixed requests have separate Operations and Development leaves. Only the
   repository-editing leaves use Development workflows. Preserve dependencies;
   execute each leaf once. Never execute the entire mixed request again as Ops.
5. Investigation of existing code retains investigation-workflow. Questions
   that only need an answer can be answered directly.

Generic verbs such as write, create and update do not prove repository editing.
Mentioning source paths, tests, coverage or an existing PR does not request edits.

Calibration examples:
- "triage these issues" → Operations.
- "open an issue for X and assign Y" → Operations.
- "create an issue about src/router.rs" → Operations.
- "write up the answers to these questions in chat" → Operations.
- "research the question set and answer in an issue" → Operations.
- "report lane status" or "coordinate review of PR 12" → Operations.
- "rename term X across docs of repos A and B" → Development in each edited repo.
- "remove a programme name from code/docs, research questions, open a cross-check
  issue for a colleague" → Development edits plus Operations research and issue
  creation. The cross-check leaf depends on the relevant results.
- "run tests and fix failures" → Operations test run plus Development fixes.
- "update README" or "fix a typo in tracked documentation" → Development.
- "what is OAuth?" → Q&A. "why is CI failing?" → Investigation.
- "CI passed on PR 12" or a PR hand-over → acknowledgement; no new workflow.
- "PR 134 is merged, retry the install" → Operations.

Actions:
Development and Investigation: announce the classification and invoke
Skill(skill="dev-orchestrator"). Mixed work: ask dev-orchestrator to dispatch the
separate classified leaves with dependencies. Operations: execute directly or
use one scoped agent. Q&A: answer directly.

Development uses default-workflow, or quick-change when selected by its trusted
workflow override. Model-supplied recipe names cannot change Operations routing.
Tracking issues are optional. Omission, null, blank and recognised placeholders
(including TBD) mean absence. If new tracking is explicitly required, create the
real issue before passing its number downstream. Never invent an issue number.
</system-reminder>
